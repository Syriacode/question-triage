# Interview questions: question-triage

## Q1. Walk me through what happens when I run `triage classify "..."`: the messages, the system prompt, the schema, constrained decoding, Pydantic validation, retries, the policy and the usage log.

Answer: `triage/cli.py` parses the arguments, builds the client with `make_client`, opens the `UsageLog` and calls `classify`. `build_messages` creates a system message holding the label definitions and a user message containing `Question:` followed by the text. `classify` generates the JSON schema from the `Triage` Pydantic model, and `OllamaClient` posts the messages and schema to `/api/chat` with temperature 0 and streaming off. Ollama uses the schema for constrained decoding: it turns the schema into a grammar and, at each step, blocks tokens that would break it, so the model can only choose among valid continuations. The reply text is then checked with `Triage.model_validate_json`; if it is invalid, the bad reply and the specific error go back as assistant and user messages, and the model tries again with no wait. If the call itself fails, `LLMError` triggers exponential backoff of 1 s then 2 s, and after 3 attempts `classify` raises `TriageError`, which the CLI prints to stderr with exit code 1. On success, `apply_policy` forces `needs_human` to true whenever urgency is high, and the CLI prints the result as JSON. Every attempt, failed or not, appends one line to `logs/usage.jsonl` with the model, attempt number, tokens, latency, cost and any error.

## Q2. The model is already constrained by a JSON schema. Why validate again with Pydantic, and what can still go wrong even when the JSON is valid?

Answer: The schema constrains generation on one provider, but Pydantic is the boundary my own code controls, and it works the same for Ollama, the fake backend or a future hosted one. Constraints can also fall short: a token limit can cut the reply off mid-JSON, and not every JSON Schema keyword is guaranteed to be enforced, such as the 300-character limit. Validation also turns a raw string into a typed `Triage` object and produces a specific error I can feed back to the model. Valid JSON only proves shape, though, not truth. In my runs the model labelled the input "test" as `assignment_help` with `high` urgency, and wrote explanations claiming things it couldn't know, such as "Explanation found in the course slides." Pydantic's lax mode also accepts `"true"` as a bool, and a prompt injection inside a question could steer the labels while still producing perfect JSON. Those failures need evals on hand-labelled questions, review of explanations and policy rules in code, not a stricter schema.

## Q3. What are tokens, why are input and output priced differently, and how would you estimate the monthly cost of 10,000 questions a day? Why temperature 0 here?

Answer: Tokens are the word-piece units a model reads and writes; in my runs that was about 243 input tokens and 38 output tokens per call. Output usually costs more because each output token needs its own step of inference, one at a time, while input tokens can be processed together and often cached. My `triage stats` output shows 9 calls, 2,190 input tokens and 343 output tokens, which costs $0.003905 at $1/$5 per million, or about $0.000434 per question. At 10,000 questions a day for 30 days, that is 300,000 questions: about 73M input tokens ($73) plus 11.4M output tokens ($57), or roughly $130 a month. That log includes one fake call, and removing it gives closer to $139, so I'd quote $130 to $140, add a margin for retries, and check how the hosted model counts tokens. Temperature 0 makes the model favour the most likely token, which suits classification because I want the best label rather than variety. It reduces variation but doesn't guarantee repeatability or correctness: in my own test, temperature 0 gave two different titles in three runs.

## Q4. Which errors should you retry and how? Cover backoff, rate limits (429), errors you should NOT retry, feeding validation errors back, attempt limits, and logging failed attempts.

Answer: Retry failures that are likely to be temporary: connection errors, timeouts, HTTP 5xx and 429 rate limits. Use exponential backoff, as my code does with 1 s then 2 s, and add random jitter in production so that many clients don't retry at the same moment. For a 429, honour the `Retry-After` header when the provider sends one, because it tells you when capacity returns. Don't retry errors that won't change, such as a 400 bad request, 401 or 403 auth failures, a missing model or an over-long prompt; my code currently wraps all HTTP errors as `LLMError`, so a production version should separate these and fail fast. Invalid output is different: waiting won't help, so send the bad reply and the specific validation error back and ask again immediately. Always keep a hard attempt limit, three here, then raise a clear `TriageError`, since an unbounded loop on a bad label turns a bug into a large bill. Log every attempt including failures: invalid replies used tokens that a hosted API would bill, so leaving them out understates cost and hides problems, while connection failures are logged with 0 tokens.

## Q5. LLM system design: design a triage service for a university help inbox with 5,000 questions a day across 200 courses, routing to a human review queue. Cover the architecture (API, queue, workers, model, database), local vs hosted model choice, latency and cost budgets, evaluation before each release, privacy of student messages (student records laws such as FERPA, and what you may send to a vendor), monitoring, and what happens when the model is down.

Answer: For architecture, an API stores each question in Postgres and places a job on a queue, then stateless workers call the model through the `LLMClient` interface, validate, apply policy and save the labels with the model and prompt version, and staff work from a human review queue built on those records. For load, 5,000 a day averages about 0.06 per second, so even a 10x peak is under 1 per second, and at my roughly 4 seconds per call a handful of workers is enough. For the model, I'd start with a local or university-hosted one for privacy and predictable cost, and move to a hosted model only if evals show a meaningful accuracy gain, at about $65 a month at my sample $1/$5 rates. Triage is asynchronous, so as a starting budget I'd target under a minute at p95 for queueing plus inference, and set a daily spend alert and cap. Before each model or prompt release, I'd run a hand-labelled set covering many courses and block the release if per-label accuracy falls or recall on truly urgent messages drops, since missing an emergency is the worst error. For privacy, messages tied to a student can be education records under FERPA, so a vendor should receive them only under an arrangement such as the school-official exception, with a contract covering direct control, use limits, no training on the data and retention, reviewed by the university's privacy office; I'd also redact identifiers where possible, restrict access and set retention periods. For monitoring, I'd track queue depth, latency, validation-failure and retry rates, cost, label drift and how often staff change a label, and audit a sample of results. When the model is down, jobs wait in the queue with backoff and a circuit breaker, anything that exhausts its attempts or waits too long goes to the human queue unlabelled, and a simple keyword rule flags possible emergencies so they never wait on the model.
